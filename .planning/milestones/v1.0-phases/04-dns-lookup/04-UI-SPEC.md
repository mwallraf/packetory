Reused unchanged: `lib/hooks/useCopyToClipboard.ts`, `lib/hooks/useKeyboardShortcut.ts`.

**Page structure (informs Spacing/Typography roles below):**
1. `h1` "DNS Lookup" (Display)
2. Domain `Input` (DNS-02/03) + record-type segmented control (A/AAAA/MX/TXT/NS/CNAME, D-09) + explicit Refresh button (DNS-05) — all in one control row
3. Inline invalid-input validation slot below the domain input (QUAL-08)
4. Result panel — exactly one of:
   - Fixed-height skeleton (D-08, first load only, before any result exists)
   - Last valid result at reduced opacity + spinner overlay (D-07, debouncing or in-flight)
   - Success state: resolver badge + lookup duration meta row, then the record list for the active type (DNS-07)
   - One of 4 distinct error-state cards: invalid-input, NXDOMAIN, empty-NOERROR, rate-limited, resolver-unavailable (D-04/D-05/D-06) — 5 states total, invalid-input renders inline near the input (step 3) rather than replacing the whole result panel, since the domain is malformed before any lookup is attempted
5. Worked example section (static, mirrors Phase 2/3's shape)
6. FAQ section (static, mirrors Phase 2/3's shape) — includes the D-02 resolver-disclosure item

## Spacing Scale

Declared values (must be multiples of 4) — inherited unchanged from Phase 1:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact element spacing (record value ↔ TTL ↔ copy button) |
| md | 16px | Default element spacing; record-list row gap, record-type toggle grid gap |
| lg | 24px | Section padding (worked-example, FAQ blocks) |
| xl | 32px | Layout gaps (between control row, result panel, worked example) |
| 2xl | 48px | Major section breaks (result section → worked example → FAQ) |
| 3xl | 64px | Page-level spacing (top/bottom page padding, matches `app/page.tsx`'s `py-12`) |

Exceptions:
- Icon-only interactive controls (per-record copy buttons, Refresh button, per-error "Try again" buttons) keep the Phase 1 minimum 44×44px hit area via padding around a smaller visual icon (16–20px), never by breaking the 4px grid — identical rule to Phase 2/3.
- Record-type segmented control (6 options, D-09) uses `grid-cols-3 grid-rows-2 sm:grid-cols-6 sm:grid-rows-1 gap-2` — wraps to a 2×3 grid below the `sm` breakpoint (640px) so 320px viewports never horizontal-scroll or clip an option; each cell still meets the 44×44px minimum. Documented here only so the executor doesn't invent an arbitrary breakpoint (same rationale as Phase 3's field-grid exception).
- Record list has no hard row cap this phase (typical record counts for common domains are single digits) — no `ScrollArea`/`max-h` constraint is applied unless implementation testing surfaces an unusually large real-world record set; if one is, use the Phase 2 batch-list precedent (`max-h-96`, already on-grid).

## Typography

Inherited unchanged from Phase 1/2/3 — same 4 declared sizes/weights, reused for this phase's content:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 14px | 600 (semibold) | 1.4 |
| Body | 16px | 400 (regular) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 32px | 600 (semibold) | 1.2 |

Phase 4 role assignments:
- **Display** — page `h1` only ("DNS Lookup"), one per page.
- **Heading** — results section heading (e.g. "A records for cloudflare.com", dynamic per active type + domain); the short label of each of the 5 error-state cards (e.g. "No such domain", D-04); section headings ("Worked example", "FAQ").
- **Body** — every record value in the result list; the resolver-used/lookup-duration meta row; the one-line plain-language explanation inside each error-state card (D-04/D-05); worked-example prose; FAQ answers; page intro paragraph.
- **Label** — domain input label, record-type toggle labels ("A", "AAAA", "MX", "TXT", "NS", "CNAME"), resolver `Badge` text ("Primary resolver" / "Fallback resolver"), field-name labels within the record row ("TTL"), Refresh/"Try again" button captions, FAQ question text, copy-button `aria-label`/visible captions.

**Monospace override** (same rule extended from Phase 1–3's address/UUID/CIDR values): Geist Mono replaces Geist Sans, at the same size/weight as the role it appears in, for every technical value on this page —
- Domain input value and the echoed domain inside the results-section Heading: Heading size/weight (20px/600) in Geist Mono where it appears in a heading, input-default size where typed.
- Every record value (A/AAAA IP, MX priority+exchange, TXT text, NS/CNAME target): Body size/weight (16px/400) in Geist Mono.
- TTL value: Body size/weight (16px/400) in Geist Mono (it's a raw technical number, same treatment as Phase 3's field values).
- Worked-example sample record values: Body size (16px/400) in Geist Mono.

**Deliberately kept in Geist Sans (not mono) [ASSUMPTION]:** the resolver `Badge` text and the lookup-duration meta text ("42ms") — these are UI status/measurement labels, not copyable technical values a user pastes elsewhere, so they follow the surrounding Label/Body sans treatment rather than the mono override rule above.

## Color

60/30/10 split — inherited unchanged from Phase 1–3 (values confirmed live in `app/globals.css`, both themes):

| Role | Light | Dark | Usage |
|------|-------|------|-------|
| Dominant (60%) | `#FFFFFF` white | `#020617` slate-950 | Page background |
| Secondary (30%) | `#F1F5F9` slate-100 | `#0F172A` slate-900 | Result panel surface, record-list row card, worked-example/FAQ surfaces |
| Accent (10%) | `#0891B2` cyan-600 | `#22D3EE` cyan-400 | See reserved list below |
| Destructive | `#DC2626` red-600 | `#EF4444` red-500 | First real use this phase — see reserved list below |

Accent reserved for (explicit list — never "all interactive elements"):
- Copy-button icon default/hover/active state + "Copied!" flash — every per-record copy action (DNS-07's core value, "one-click copy everywhere")
- Explicit Refresh button (DNS-05) — the page's core repeatable action, direct analogue of Phase 2's Regenerate button
- Active/selected state of the record-type segmented control (D-09) — a tint on the currently selected option only, not the whole control (same rule as Phase 2's version toggle)
- In-flight spinner icon (D-07's loading indicator over the dimmed last-valid result)
- Keyboard focus ring (all interactive elements — inherited global rule)

Destructive reserved for **[ASSUMPTION — CONTEXT.md's D-04 requires "distinct icon + label," not a specific color assignment; this spec makes the explicit split below]**:
- Rate-limited error card (icon, border accent, "Try again" button, D-06) — a genuine service-side failure condition
- Resolver-unavailable error card (icon, border accent, "Try again" button, D-06) — a genuine service-side failure condition
- Rationale: these two states represent an actual malfunction the user should treat with more urgency than a routine negative DNS answer; using destructive here also gives QUAL-08's 5 states real visual differentiation beyond icon+copy alone, satisfying D-04's "not just color-coding" instruction by pairing color with icon+label rather than relying on color alone.

Deliberately kept neutral (muted surface + outline, not destructive, not accent), to avoid over-alarming the user about a legitimate DNS answer:
- Invalid-input inline validation (matches Phase 3's neutral treatment of invalid CIDR input — a user-correctable typo, not a system failure)
- NXDOMAIN error card — a legitimate, valid DNS answer ("this domain doesn't exist"), not a failure; muted icon/border, per D-05's plain-language distinction from resolver-unavailable
- Empty-NOERROR error card — equally a legitimate valid DNS answer ("this domain exists, no records of this type"); same neutral treatment as NXDOMAIN
- Resolver `Badge` (Primary/Fallback indicator) — neutral/outline badge, consistent with Phase 3's family-badge guidance to reserve accent for specific action elements only
- Record value text, TTL, lookup-duration meta — plain `text-foreground`/`text-muted-foreground`, never accent-colored (informational, not actionable)
- Worked-example card border, FAQ section styling

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | "Refresh" — icon+label button (`RefreshCw`), `aria-label="Refresh lookup"`; re-runs the current domain+type lookup immediately (DNS-05), same immediate-trigger path as paste/Enter |
| Secondary CTA — per-record copy | "Copy" — icon-only button (`Copy`/`Check` swap, "Copied!" `aria-label`) next to every record value in the result list |
| Empty state (page-level) | Not applicable — D-10 guarantees `cloudflare.com`/type `A` auto-resolves on load (DNS-01); the page never shows a blank/pre-lookup state after mount |
| Error state — invalid input | "Enter a valid domain name, like cloudflare.com or example.co.uk." — shown inline below the domain input via `aria-invalid` + `aria-describedby`, never a popup/reload (QUAL-08); the last valid result stays visible and unchanged while this message shows (D-07's "keep last valid result" principle extended to this state) |
| Error state — NXDOMAIN (D-05) | Short label: "No such domain." Explanation: "{domain} doesn't exist." |
| Error state — empty-NOERROR (D-05) | Short label: "No {TYPE} records." Explanation: "{domain} exists but has none of this type." |
| Error state — rate-limited (D-06) | Short label: "Too many lookups." Explanation: "Please wait a moment and try again." + inline "Try again" button in the card itself |
| Error state — resolver-unavailable (D-06) | Short label: "Resolvers unreachable." Explanation: "DNS resolvers are unreachable right now — check your connection and try again." + inline "Try again" button in the card itself |
| Error state — copy failure | "Couldn't copy — select the text and copy manually." — identical wording to Phase 1–3's `useCopyToClipboard` pattern, reused verbatim; independent per-record confirmation state (no cross-record bleed) |
| Resolver disclosure (D-02) | FAQ answer text (verbatim intent, exact wording finalized in content phase): "Lookups are sent to Cloudflare (primary) and, only if Cloudflare is unavailable, Google (fallback) — the domain you enter is never stored or sent anywhere else." Same disclosure principle applies to the privacy notice per D-02. |
| Destructive confirmation | None — no destructive actions exist; typing a new domain, switching record type, or clicking Refresh instantly replaces the displayed result and URL, nothing is destroyed or persisted to lose |

|----------|------------|--------|---------------------|
| empty | domain-input + result (page-level) | ✅ covered | D-10 guarantees `cloudflare.com`/type `A` auto-resolves on load (DNS-01) — no reachable "nothing has ever been looked up" state after mount, same reasoning as Phase 2/3's always-populated defaults. |
| empty | record-list (per-lookup, list-collection) | ✅ covered | A lookup that returns zero records for the active type is itself one of the 5 explicit QUAL-08 states (empty-NOERROR), rendered as its own distinct card rather than a blank/placeholder list — see Copywriting Contract. |
| loading | result-panel (form + list-collection) | ✅ covered | D-07: while debouncing or in-flight (any trigger), the last valid result stays visible at reduced opacity with a spinner overlay, never a full clear or a silent full-brightness wait. | error | domain-input + result-panel (form) | ✅ covered | All 5 QUAL-08 states (invalid input, NXDOMAIN, empty-NOERROR, rate-limited, resolver-unavailable) render their own icon + short label + one-line explanation (D-04), never a popup/reload; rate-limited/resolver-unavailable additionally carry their own "Try again" button (D-06). |
| populated | record-list (list-collection) | ✅ covered | Successful lookup renders N normalized records for the active type (DNS-06/07); resolver-used badge and lookup duration are shown once per lookup at the top of the panel, not repeated per record. |
| partial | record-list (list-collection) | ✅ covered | `resolveWithFallback` (04-RESEARCH.md Pattern 3) returns one atomic response from exactly one resolver per lookup — there is no reachable "half-loaded" record list; a genuine resolver failure short-circuits straight to the resolver-unavailable state instead of a partially populated grid. |
| zero-one-many | record-list (list-collection) | ✅ covered | 0 records → empty-NOERROR card (see empty row above); 1–N records → the same list rendering regardless of count, no singular/plural copy variant needed since rows are technical values (IPs, hostnames) rather than counted nouns. |
| overflow | record-list values — TXT/MX/NS/CNAME (list-collection) | 🧪 backstop | TXT records (up to 255 chars, e.g. a full SPF/DKIM string) and long MX/NS/CNAME target hostnames must wrap, never clip, at 320px. Needs a visual test with a real long-TXT domain (e.g. `cloudflare.com`'s own TXT set, which already includes SPF-length records per 04-RESEARCH.md's live-verified quirks). |
| long-text | domain-input value (form) | 🧪 backstop | A near-maximum-length domain (up to 253 chars, `lib/dns/validate.ts`'s `MAX_DOMAIN_LENGTH`) must not break the control-row layout at 320px — input scrolls/wraps internally rather than forcing horizontal page scroll. Needs a visual test at 320px with a long valid domain string. |
| overflow | record-type-toggle — 6-way segmented control (interactive-control) | ✅ covered | Wraps to a 2-row × 3-column grid below the `sm` breakpoint (640px), single row above — resolved explicitly in Spacing Scale exceptions so the executor doesn't invent an arbitrary breakpoint; each option keeps the 44×44px minimum touch target at 320px. |
| error | copy-actions (interactive-control, repeated per record) | ✅ covered | Reuses `lib/hooks/useCopyToClipboard.ts` unchanged (Phase 1–3 pattern) — a rejected clipboard write shows the same inline "Couldn't copy" message per record, independent confirmation state per record instance (no cross-record bleed). |
| unresolved | result-panel state for RCODE 2 (SERVFAIL) | ⚠ unresolved | 04-RESEARCH.md's Assumption A1 (SERVFAIL treated as a genuine-failure trigger for fallback) is a backend/logic decision, not a UI-state gap in isolation — but if the planner instead decides SERVFAIL should render directly rather than trigger fallback, no UI state currently covers that outcome distinctly from resolver-unavailable. Planner must either (a) confirm SERVFAIL always triggers fallback per A1 (in which case it never surfaces as its own UI state — a successful fallback renders normally, a failed fallback renders as resolver-unavailable), or (b) explicitly add a 6th UI state if SERVFAIL is meant to be shown to the user distinctly. Flagged here so this ambiguity isn't silently dropped. |
| overflow / long-text | worked-example, FAQ (static-content) | ✅ covered | Same as Phase 1–3 — static build-time copy, standard prose wrap, no variable-length/user-generated input risk. |
