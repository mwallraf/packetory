<objective>
Close the single remaining Phase 4 verification gap: the DNS-04 race-safety guard was only wired into the
INVALID-input branches of `handleDomainChange`/`handleDomainPaste` (commit a63c8aa). The VALID branch of
`handleDomainChange` still schedules a new debounce without first cancelling an already-in-flight lookup, so
a slow earlier request's stale response can still render after the user has typed a newer, different valid
domain whose own debounce has not yet fired. This is a one-line logic gap plus its regression test.

Purpose: `handleDomainChange`'s valid branch is the last un-guarded transition. Wiring `cancelInFlightLookup()`
into it makes the DNS-04 / ROADMAP Phase 4 Success Criterion 4 guarantee ("a slower earlier response can never
overwrite a newer result on screen") hold universally — for valid-domain edits, not just invalid ones.

Output: the fix in `app/tools/dns/DnsTool.tsx` (valid branch of `handleDomainChange` now calls
`cancelInFlightLookup()` before `scheduleDebouncedLookup()`), and a new E2E regression test in
`tests/e2e/dns-lookup.spec.ts` that reproduces the typed-debounce-vs-in-flight race and proves the stale
response never renders.

Depends on 04-01 (created `DnsTool.tsx`) and 04-02 (added the DNS-04 E2E race describe + last modified
`DnsTool.tsx`/`dns-lookup.spec.ts`). Both are complete; this is the only plan in this gap-closure batch, so
wave 1.

    branch, which already calls `cancelInFlightLookup()` before its own `setState`.

    Why this fixes the gap: when an earlier debounced lookup has already fired, `runLookup` has stored its
    `AbortController` in `abortControllerRef.current` and captured a `seq` from `requestSeqRef.current`, and its
    fetch is in flight. Typing a new valid domain currently only calls `scheduleDebouncedLookup()`, which clears
    the (already-fired, now-null) debounce timer and sets a fresh one — it never aborts the in-flight controller
    nor bumps `requestSeqRef.current`. So when the stale fetch resolves, `runLookup`'s `seq !== requestSeqRef.current`
    guard still passes (the seq was never bumped) and the stale result renders. Calling `cancelInFlightLookup()`
    first aborts `abortControllerRef.current` and increments `requestSeqRef.current`, so the stale response now
    trips either `if (controller.signal.aborted) return;` or `if (seq !== requestSeqRef.current) return;` inside
    `runLookup` and never reaches `setState`. The subsequent `scheduleDebouncedLookup()` then arms the new
    domain's debounce as before.

    Scope discipline: change ONLY the valid branch of `handleDomainChange`. Do not touch `handleDomainPaste`,
    `handleTypeChange`, `handleRefresh`, `handleTryAgain`, or the immediate-trigger paths — those call
    `runLookup` directly (via `runLookupImmediate`), which already aborts + bumps the sequence token and is
    already race-safe. Do not rename or re-signature `cancelInFlightLookup`, `scheduleDebouncedLookup`, or
    `runLookup`. This is a one-line addition (plus, optionally, a short inline comment citing DNS-04 and the
    CR-01 sub-case it closes).
