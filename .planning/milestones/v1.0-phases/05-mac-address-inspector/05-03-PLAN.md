<objective>
Third and final vertical slice: the vendor lookup — and the phase's signature architectural seam, the API-route/core-logic separation. Building on 05-02's classification, a non-randomized MAC now also resolves its vendor/organization name through a brand-new server-side Route Handler (app/api/mac-vendor/route.ts, the first upstream-fetching route in the codebase) that proxies to maclookup.app. Critically, only the 6-hex OUI ever crosses to the server (MAC-10 by construction), the lookup is debounced + session-cached (D-03), randomized addresses skip the call entirely (D-12), and any failure degrades to a neutral note while classification stays fully intact (MAC-08, D-11).

Purpose: Ship vendor identification (MAC-03), prove the API-route/core-logic separation that this whole phase exists to establish, and lock in the privacy-by-construction and vendor-failure-resilience contracts.
Output: the route (+ first route test in the codebase), lib/mac/vendor.ts client+cache (+ tests), the wired vendor field + copy-all in MacTool.tsx, the vendor e2e scenarios, and the MAC-10 analytics regression guard.
</objective>

| T-05-02 | Information Disclosure | full MAC → server/logs/analytics/upstream | high | mitigate | Only the OUI (6 hex) is ever sent (Pattern 3, privacy-by-construction); `mac`/`oui` never added to DEFAULT_ALLOW_LIST (regression-guarded in Task 3); Phase 1 beforeSend strips any non-allow-listed param. |
