| Keyboard `Ctrl/Cmd+C` target **[ASSUMPTION]** | Copies the complete result as a single formatted text block (all 4 formats + OUI + vendor + U/L + I/G + randomization flag) via the "Copy all" affordance (MAC-09) — mirrors Phase 2's "Copy all" batch behavior, adapted to one MAC's full field set instead of a batch of values |

**Shadcn components required this phase:** none new to install — all already present in `components/ui/`: `Input`, `Label` (MAC field), `Badge` (U/L, I/G, randomization-hedge, vendor-state pills — D-08), `Button` (not required as a distinct primary CTA this phase — see Copywriting Contract), `Separator` (between result panel and worked example/FAQ), `Tooltip` (optional — badge explanations render inline per D-08, not hidden behind hover, so `Tooltip` is not required this phase). Reused unchanged: `lib/hooks/useCopyToClipboard.ts`, `lib/hooks/useKeyboardShortcut.ts`.

**Page structure (informs Spacing/Typography roles below):**
1. `h1` "MAC Address Inspector" (Display)
2. MAC address `Input` (MAC-01) — single free-text field, no record-type/mode toggle needed this phase (unlike DNS's 6-way segmented control or UUID's version toggle)
3. Inline "incomplete address" note below the input when mid-edit and syntactically invalid (D-07) — same visual slot pattern as DNS's invalid-input note, but this state is expected/routine (a user is still typing), not an error condition, so it renders neutral, not destructive
4. Result panel — exactly one of:
   - Fixed-height skeleton (mirrors DNS/Subnet's loader boundary skeleton, first paint only, before the client island hydrates)
   - Full result at reduced opacity (D-07 "dimmed/stale" — mid-edit with an incomplete MAC, last valid result still fully rendered underneath)
   - Full result at normal opacity (a complete, valid MAC is currently entered)
5. Within the result panel, three grouped sections, top to bottom:
   a. **Normalized formats** — all 4 simultaneous variants (colon/dash/dot/none, D-05), each individually copyable, plus one "Copy all" action for the complete result (MAC-09)
   b. **Classification badges row** — U/L badge, I/G badge, and (conditionally) the randomization-hedge badge (D-08/D-09), each with its one-line plain-language explanation directly beneath/beside it
   c. **Vendor field** — OUI prefix (MAC-04, always shown) + vendor name/state (MAC-03/MAC-08/D-11/D-12), one of 4 vendor-field states (see Copywriting Contract)
6. Worked example section (static, mirrors Phase 2/3/4's shape)
7. FAQ section (static, mirrors Phase 2/3/4's shape) — includes the D-01/D-02 vendor-lookup-is-a-proxy disclosure and the D-09/D-10 randomization-heuristic explanation

## Spacing Scale

Declared values (must be multiples of 4) — inherited unchanged from Phase 1:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact element spacing (format value ↔ copy button; badge icon ↔ badge label) |
| md | 16px | Default element spacing; format-list row gap, badge-row gap |
| lg | 24px | Section padding (worked-example, FAQ blocks; gap between the 3 grouped result sections — formats / classification / vendor) |
| xl | 32px | Layout gaps (between input row, result panel, worked example) |
| 2xl | 48px | Major section breaks (result section → worked example → FAQ) |
| 3xl | 64px | Page-level spacing (top/bottom page padding, matches `app/page.tsx`'s `py-12`) |

Exceptions:
- Icon-only interactive controls (per-format copy buttons, "Copy all" button) keep the Phase 1 minimum 44×44px hit area via padding around a smaller visual icon (16–20px), never by breaking the 4px grid — identical rule to Phase 2/3/4.
- The 4-format list (colon/dash/dot/none, D-05) uses a single-column stacked layout at all viewport widths (`flex flex-col gap-2`) rather than a grid — unlike DNS's 6-way toggle, these are 4 read-only, individually-copyable output rows, not a selector control, so no responsive grid-to-column reflow logic is needed; each row's `font-mono` value uses `break-all` to guarantee no horizontal scroll at 320px (identical wrapping rule to Subnet/DNS field values).
- The classification badge row (U/L + I/G + optional randomization-hedge, D-08) wraps via `flex flex-wrap gap-2` at narrow widths — no fixed grid, since the row holds 2–3 items only (never a 6-item toggle-scale count), so simple wrap-flow is sufficient without inventing a breakpoint.

| Heading | 20px | 600 (semibold) | 1.2 |

Phase 5 role assignments:
- **Display** — page `h1` only ("MAC Address Inspector"), one per page.
- **Heading** — each of the 3 grouped result-section labels ("Normalized formats", "Classification", "Vendor"); section headings ("Worked example", "FAQ").
- **Body** — every format-variant value (colon/dash/dot/none); the one-line plain-language explanation beneath each classification badge (D-08/D-09); the vendor name/state text; worked-example prose; FAQ answers; page intro paragraph.
- **Label** — MAC input label, format-row field labels ("Colon", "Dash", "Cisco (dot)", "No separator"), classification badge text ("Universally Administered", "Unicast", "Likely randomized (privacy MAC)"), OUI prefix field label, "Copy" / "Copy all" button captions, FAQ question text, copy-button `aria-label`/visible captions.

**Monospace override** (same rule extended from Phase 1–4's address/UUID/CIDR/record values): Geist Mono replaces Geist Sans, at the same size/weight as the role it appears in, for every technical value on this page —
- MAC input value: input-default size in Geist Mono (matches CIDR/domain input precedent).
- Every one of the 4 normalized format values (colon/dash/dot/none): Body size/weight (16px/400) in Geist Mono.
- OUI prefix value (MAC-04): Body size/weight (16px/400) in Geist Mono.
- Worked-example sample MAC/format/OUI values: Body size (16px/400) in Geist Mono.

**Deliberately kept in Geist Sans (not mono) [ASSUMPTION]:** classification badge labels ("Universally Administered", "Unicast", "Likely randomized (privacy MAC)") and the vendor company name — these are human-readable labels/names, not raw technical values a user pastes elsewhere, so they follow the surrounding Label/Body sans treatment rather than the mono override rule above (same reasoning DNS applied to its resolver badge text).

## Color

60/30/10 split — inherited unchanged from Phase 1–4 (values confirmed live in `app/globals.css`, both themes):

| Role | Light | Dark | Usage |
|------|-------|------|-------|
| Dominant (60%) | `#FFFFFF` white | `#020617` slate-950 | Page background |
| Secondary (30%) | `#F1F5F9` slate-100 | `#0F172A` slate-900 | Format-row cards, classification badge/section surfaces, vendor-field surface, worked-example/FAQ surfaces |
| Accent (10%) | `#0891B2` cyan-600 | `#22D3EE` cyan-400 | See reserved list below |
| Destructive | `#DC2626` red-600 | `#EF4444` red-500 | Not used this phase — see rationale below |

Accent reserved for (explicit list — never "all interactive elements"):
- Copy-button icon default/hover/active state + "Copied!" flash — every per-format copy action, the OUI copy action, and the single "Copy all" action (MAC-09's core value, "one-click copy everywhere")
- Keyboard focus ring (all interactive elements — inherited global rule)

Destructive is **NOT used anywhere in this phase [explicit decision, extending DNS's precedent]:**
- Unlike DNS (which has 2 genuine service-failure states — rate-limited, resolver-unavailable), this phase has no equivalent "the system is broken" condition. MAC-08/D-11's "vendor lookup unavailable" is an expected, routine, non-alarming outcome (the interim API proxy is explicitly documented as sometimes-unreliable, per D-01/RESEARCH.md) — rendering it as destructive/red would overstate its severity and contradict D-11's own instruction to show "a neutral inline note ... not an error banner." All 4 vendor-field states (normal / not-found-in-registry / lookup-unavailable / not-applicable-randomized) and the "incomplete input" note (D-07) use neutral secondary-surface treatment only.
- If a future phase introduces a genuine MAC-tool failure mode (e.g. the `/api/mac-vendor` route itself returning a 5xx the client can't classify), destructive should be reserved for that specific new state — not retrofitted onto today's 4 vendor states, none of which represent an actual malfunction from the user's perspective.

Deliberately kept neutral (muted surface + outline, not destructive, not accent):
- "Incomplete input" note (D-07) — matches Phase 3/4's neutral treatment of an in-progress, user-correctable edit; this is expected mid-typing behavior, not an error.
- U/L badge, I/G badge — neutral/outline `Badge` variant regardless of which state (universal vs. local, unicast vs. multicast) — informational classification, not a warning; per D-08 the plain-language explanation, not color, carries the distinction (never color-alone, QUAL-05).
- Randomization-hedge badge (D-09) **[explicit decision]** — neutral/outline, NOT destructive and NOT accent. This is a privacy-relevant heads-up, not a system error and not a call-to-action; a distinct icon (`ShieldAlert`) + the exact locked wording carries the signal (D-09's own hedge language already does the communicative work — adding red would misrepresent "likely randomized" as something dangerous or broken).
- Vendor field, all 4 states — plain `text-foreground` (found) / `text-muted-foreground` (not-found / unavailable / not-applicable) — informational, not actionable.
- OUI prefix value, format-variant values — plain `text-foreground`, never accent-colored (informational, not actionable — matches DNS's record-value treatment).
- Worked-example card border, FAQ section styling.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA — "Copy all" | "Copy all" — icon+label button (`Copy`/`Check` swap), copies the complete result as one formatted text block (MAC-09); mirrors Phase 2's "Copy all" batch action |

| Empty state (page-level) | Not applicable — D-06 guarantees a real, recognizable demo MAC auto-populates the full result on load (zero-effort default); the page never shows a blank/pre-input state after mount |
| Incomplete-input state (D-07) | "Keep typing — enter all 12 hex digits (e.g. 00:1A:2B:3C:4D:5E)." — shown inline below the MAC input; the last valid result stays fully visible underneath at reduced opacity (not blanked), matching D-07's "dimmed/stale" instruction |

| Classification — U/L, Locally Administered (D-08) | Badge: "Locally Administered." Explanation: "Set by software rather than assigned by a vendor — common for virtual adapters and privacy-randomized addresses." |
| Classification — I/G, Unicast (D-08) | Badge: "Unicast." Explanation: "Addressed to a single device." |
| Classification — I/G, Multicast (D-08) | Badge: "Multicast." Explanation: "Addressed to a group of devices." |
| Randomization hedge (D-09, locked verbatim) | Badge: "Likely randomized (privacy MAC)." Explanation: "This address has the locally-administered bit set, a pattern used by iOS/Android/Windows MAC randomization — it may not reflect the device's real hardware vendor." |
| Vendor state — found (MAC-03) | "{Company name}" shown directly as the vendor value, no extra qualifier needed — a successful, positive match |
| Vendor state — not found in registry **[new 4th state, resolved per 05-RESEARCH.md Open Question 1 — NOT the same copy as "lookup unavailable"]** | "Not found in OUI registry." — a genuine negative answer from a working lookup, distinct from a failed lookup; renders in the same neutral `text-muted-foreground` treatment as the other non-error vendor states |
| Vendor state — lookup unavailable (D-11, locked wording) | "Vendor: lookup unavailable." — neutral inline note, never an error banner; the rest of the result panel (all 4 formats, OUI prefix, U/L, I/G, randomization flag) renders normally and is unaffected (MAC-08) |
| Vendor state — not applicable / randomized (D-12, locked wording) | "Vendor: not applicable (randomized address)." — shown instead of attempting a lookup at all when the address is already flagged locally-administered/likely-randomized (D-10) |
| Error state — copy failure | "Couldn't copy — select the text and copy manually." — identical wording to Phase 1–4's `useCopyToClipboard` pattern, reused verbatim; independent per-field confirmation state (no cross-field bleed) |
| Privacy/vendor-proxy disclosure (D-01/D-02/MAC-10) | FAQ answer text (verbatim intent, exact wording finalized in content phase): "Vendor lookups only send the first 3 bytes (the OUI) of your MAC address to our server, which checks a public vendor database — the rest of the address never leaves your browser and is never stored or sent to analytics." |
| Destructive confirmation | None — no destructive actions exist; typing a new MAC instantly replaces the displayed result, nothing is destroyed or persisted to lose |
